# Chat reads go through a read-only role over owner-rights chat views

The Overview chat lets a model write SQL, so the database, not the prompt, has to be the boundary. `chat_query(q)` is a Postgres function called with the member's own session. It is `security definer` and owned by `chat_reader`, a login-less role whose only privilege is `select` on the `v_chat_*` views, so the query runs as `chat_reader`. It turns the transaction read-only and runs the query wrapped in a 500-row limit. `chat_reader` has no grant on any table, on `v_sales`, `v_customers`, `settings` or `team_members`, so a query that names them fails with a permission error. The chat views are owner-rights (like the public catalog views, [ADR 0003](0003-public-views-bypass-rls.md)) and each filters on `is_member()`, but that filter reads a setting the query itself can overwrite, so `chat_query` also refuses a non-member before it runs the query.

The alternatives were a separate database connection with its own secret, and a fixed set of canned queries. The connection adds a secret and a second place for credentials to leak; canned queries cannot answer a question nobody thought of. A role plus views keeps the member's session as the only credential and lets the privilege system say what the model may see.

Two consequences shape the views. Customer names and phones must never reach the model, so `v_chat_sales` and `v_chat_customers` carry a `customer_alias` (`C-` and the first six characters of the customer id) instead of a name or phone, and no chat view carries `created_by`, `updated_by` or `notes`. And because Postgres checks table privileges as the view owner but function privileges and nested `security_invoker` views as the caller, the chat views cannot sit on top of `v_yard_batches`, `v_sales` or `v_dashboard_kpis`; they restate those queries over the tables. `chat-query.test.ts` compares each chat view with the view it mirrors so the two cannot drift apart unnoticed.

The first design switched role with `set local role chat_reader` inside an ordinary function. That is escapable: `SET ROLE` is checked against the connection's login role (`authenticator`), which belongs to `authenticated` and `service_role`, so a query could call `set_config('role', ...)` and, through `query_to_xml`, read customers as that role in the same statement. A scan of the query or plan for `set_config` does not close it, because the function name can be built at run time (`concat('set_', 'config')`, `chr()`, `format()`). The role must instead be impossible to change while the query runs. Postgres refuses `set_config('role', ...)` and `set_config('session_authorization', ...)` inside a security-definer function, however deeply nested, and refuses to turn a read-only transaction back to read-write once a query has run. Owning the function by `chat_reader` gets both: the query runs as `chat_reader` and cannot leave it. `chat_reader` is given `create` on `public` only for the moment `alter function ... owner to` needs it, and that is revoked in the same migration.

Owning the function by `chat_reader` fixes who the query is, not what it can touch: `chat_reader` still holds every privilege of `public`, and Postgres has no way to deny one role a `public` grant. A query can call any `public` function and set any custom setting, which is enough to forge `request.jwt.claims`, read `request.headers` (the member's bearer token), take a session advisory lock that stays on the pooled connection, or leave a session-level setting such as `request.jwt.claim` for the next request on that connection. Listing forbidden functions fails the same way the `set_config` scan did, since names can be built at run time. So `chat_query` decides membership once before the query runs, empties the request settings the query does not need, runs the query inside a sub-transaction that is always rolled back (which undoes session-level settings and notifications), and releases advisory locks afterwards, on every exit. The rows survive because plpgsql keeps local variables across a rollback. What stays reachable is whatever `public` can read, including database-level settings such as `app.settings.jwt_secret` on the local stack; a hosted project that sets one needs it cleared, since no guard inside the function can hide it.
