# Phase 1 Decisions

Outcome of the grilling session on 11 Sep 2026. Vocabulary lives in `CONTEXT.md`; this file holds the rules and computed definitions that are not glossary material.

## Malleability first

This is the first iteration after one rough call with the client. Expect heavy change in design, business rules and API. Every choice below is provisional, and the build follows these principles so change stays cheap:

- Store raw facts, derive everything else. Per-piece prices and quantities are stored; totals, margins, Age, Ageing Band, Stock Lines, Sold Out and Clamps are computed in views. Changing a formula is a view edit, not a data migration.
- No Postgres `enum` types. Categorical columns (Slot, Customer Type, Payment Mode, Role, Category) are `text` with a check constraint, so adding or renaming a value is one small migration.
- Rules live in a handful of SQL functions and views (see ADR 0001), so a rule change touches one place and is covered by one test, regardless of how many screens use it.
- Inputs rejected by constraints reachable through the UI or documented API raise a readable business-rule message before the database constraint fires, rather than exposing raw Postgres text.
- Screens are thin: server components read views, forms call functions. UI can be reshaped without touching data.
- Nothing is pre-optimised for scale or multi-tenancy. Add it when a second yard exists.
- When a rule here is changed, update this file and `CONTEXT.md` in the same commit rather than letting the docs drift.

## Stock model

- Product > Variant > Batch in storage, but Variant is hidden from every screen. New Batches get the Product's "Standard" Variant; older Variants stay stored. Stock Lines, Clamps and the Public Catalog group by Product and Size only, so stock that differs only by Variant reads as one line. Size (L ft, B ft, T mm) lives on the Batch.
- Size is required for Granite and Tiles, null for Memorial. Grouping treats null Size as one group per Product.
- Slot is stored text: one of the built-in 4FT, 5FT, DOOM, CUSTOM or a name the operator types (trimmed, up to 20 characters). It is defaulted by rule and overridable in the inward form and the Edit dialog:
  - Memorial → DOOM
  - 4 ≤ length < 5 → 4FT
  - 5 ≤ length < 6 → 5FT
  - anything else → CUSTOM
- Every new Batch records its Stack: a Slot plus a typed Batch number (shown to users as "Batch number", up to 20 characters, trimmed). `create_batch` refuses a Batch without one; a Correction keeps the existing number unless a new one is given. The inward form offers recently used Slot and Batch number pairs (`v_recent_stacks`) and an Add dialog for a new pair, whose slot picker lists the built-in slots plus every typed slot already used and can add a new one. Batches from before this rule have no Stack.
- Batch Code format `{PRODUCT_ABBR}-{DDMON}{YY}-{seq}` (e.g. `BP-07SEP26-01`). Abbreviation stored on Product, unique, auto-suggested from initials and editable. Sequence resets per product per day. Generated inside the insert function. Purchase dates before 2000-01-01 are refused so the two-digit year remains unambiguous for the supported history.
- Freight is part of the Unit Purchase Price: the Inward form and the Edit dialog do not ask for a Freight Cost, so a new or edited Batch has `freight_cost` 0 and its Landed Cost is the Area times the Unit Purchase Price entered. A one-time migration folded stored freight into the price (`unit_purchase_price = landed_cost`, `freight_cost = 0`), so no Batch's Landed Cost changed and Sales kept their snapshots. The `freight_cost` column and the RPCs' `p_freight_cost` parameter remain.
- The Unit Purchase Price is per square foot for sized Batches and per piece for Memorial. Area = length_ft * breadth_ft. A one-time migration divided every sized Batch's stored per-piece price by its Area (stored as `numeric(22,10)`), and refuses to run if any Landed Cost would change, so inventory value and Sales were untouched.
- Landed Cost = coalesce(Area, 1) * unit_purchase_price + freight_cost / initial_units, rounded to paise, stored as a generated column. Sales snapshot the Landed Cost at time of sale; Sale Price stays per piece. A price whose Landed Cost would reach ₹1,000 crore is refused ("Landed Cost per piece is too large").
- Total cost = initial_units * landed_cost, so it always equals Pieces times the Landed cost shown beside it, derived in `v_batches` as `total_cost` and shown in Recent batches after Landed cost, for live and archived Batches. Nothing is stored; the client reads what a whole Batch cost without multiplying by Pieces.
- Money is `numeric(12,2)`; percentages `numeric(5,2)`. UI formats as whole rupees.
- Products, Suppliers and Customers are created from the inward and sell forms, through the Add button beside each select or the select's inline Add row. Admins can edit, archive or delete a Product or Supplier straight from its picker on Inward, and in the Settings list, which also shows archived rows and unarchives them. Delete only when no Batch references the row (FK restrict); the refusal suggests archiving instead. Deleting a Product removes its unused Variants with it. An archived Product or Supplier leaves the Inward pickers and `create_batch` refuses it; a Correction may keep a Batch on its current archived one but cannot move a Batch onto one. No merge tool.
- Customer phone is unique when present (compared on the last ten digits); adding a customer with a phone already on file selects that customer instead. Walk-in Customer is a seeded row with no phone. The Walk-in Customer flag is immutable for every role.

## Selling

- One Sale = one Batch. Multi-batch purchases are recorded as multiple Sales, grouped by a Bill.
- A Bill (`bills`: customer, sale date, audit columns, no money) groups the Sales of one purchase through a nullable `sales.bill_id`; Sales recorded before Bills keep null. `record_bill(customer, sale date, payments, lines)` takes lines of {batch_id, quantity, sale_rate, has_stickering, stickering_cost_rate, stickering_rate} as jsonb, runs every line through the same per-Sale rules as `record_sale`, and saves all lines or none. Quantities on the same Batch across lines are checked against its Available one line after another, so together they cannot exceed it. Zero lines is refused. A Sale on a Bill keeps the Bill's customer and sale date: `correct_sale` refuses changing either on it, and the Edit sale dialog shows them read-only; quantity, price, stickering, Batch and the Bill's Payment Split stay editable. Bills have a select policy for members and no write policy; only `record_bill` writes them, and `delete_bill(bill)` (Admin only) deletes a Bill with all its Sales in one transaction, returning each line's pieces to its Batch; an unknown Bill is refused ("Unknown bill"). There is no Edit bill: a wrong customer or date on a Bill is fixed by deleting it and selling again, and a wrong Payment Split is fixed from Edit sale. `v_sales` exposes `bill_id`.
- Payment Split: `bill_payments` (bill, payment_mode text with check, amount, primary key bill plus mode) holds how each Bill was paid; `sales.payment_mode` is null on a Bill Sale and required on a Sale without a Bill, and `bills` has no payment mode. `payments` is a jsonb array of {payment_mode, amount}. One payment takes the Bill total and its amount is ignored. Two or more must each have an amount above zero and add up exactly to the Bill total ("Payments add up to ₹45000 but the bill total is ₹50000"); a repeated mode, a missing amount or an empty list is refused. Members cannot write `bill_payments`; only `record_bill`, `correct_sale` and `delete_sale` do. A migration gave every earlier Bill one payment of its full total in its old mode.
- Corrections keep the split adding up. `correct_sale` and `delete_sale` take an optional `p_payments`: given, it replaces the split and is checked against the new total, so a split-only fix is an edit that changes nothing else. Not given, a one-payment Bill follows its new total and a split Bill whose total changed is refused ("The bill total is now ₹48000; enter how it was paid"). A split on a Sale without a Bill is refused.
- Sell Stone: the Payment Mode chips are multi-select (tap again to remove, at least one stays). With two or more, the Order Summary shows "Customer pays" and an amount box per mode; the last picked mode fills itself with the rest. Edit sale on a Bill Sale shows the Bill total and the same chips and boxes; the delete confirm does too when the Bill has a split and other Sales stay. The customer page shows each Bill's payments under its item count.
- The Sale Rate is what the Customer pays per square foot of Area for the stone (per piece for Memorial). A Sale stores the rate as typed (`sale_rate`, `numeric(22,10)`) and the Area of one piece at the time of sale (`area_sqft`, the Batch's length_ft * breadth_ft, null for Memorial). `sale_price` is a stored generated column, `round(coalesce(area_sqft, 1) * sale_rate, 2)`, so the Sale Price stays per piece and every view and function that reads it is unchanged. 10 pieces of 4 × 2 ft at ₹250 per sq ft store area_sqft 8 and sale_price 2,000, a stone total of ₹20,000.
- Sell Stone and Edit sale take the Sale Rate under the label "Stone Sale Price (₹)", hint "Per sq ft" for sized stone and "Per piece" for Memorial. `record_sale` and `correct_sale` take `p_sale_rate`; `record_bill` lines carry `sale_rate`; the old `p_sale_price` signatures are gone. A missing, non-numeric or negative rate is refused ("Sale rate is required", "Sale rate must be a number", "Sale rate must be zero or more"), as is a rate whose per piece Sale Price would reach ₹1,000 crore ("Sale Price per piece is too large").
- `area_sqft` is snapshotted from the locked Batch when a Sale is recorded. `correct_sale` keeps the Sale's `area_sqft` when the Batch is unchanged and takes the new Batch's when the Batch changes, the same rule as Landed Cost. A one-time migration converted every earlier Sale (rate = old per piece price / its Batch's Area) and refuses to run if any Sale Price would change, so revenue, margin and every KPI were untouched.
- `v_sales` and `v_chat_sales` expose `sale_rate` and `area_sqft` beside the derived `sale_price`. A sale line reads `{qty} × {area} sq ft × ₹{rate}/sq ft = ₹{stone total}`, and `{qty} × ₹{rate} = ₹{stone total}` for Memorial; it no longer carries a Stickering suffix.
- Stickering follows the Sale Rate pattern. A Sale stores two rates as typed, `stickering_rate` (what the Customer pays per square foot) and `stickering_cost_rate` (what the engraver is paid per square foot), both `numeric(22,10)` default 0 and never negative; for Memorial, which has no Area, they are per piece. `stickering_price` and `stickering_cost` are stored generated columns, `round(coalesce(area_sqft, 1) * rate, 2)`, so they keep their per piece meaning and every view, Margin figure, dashboard and Ask query reads them unchanged. 4 pieces of 5 × 3 ft at ₹60 per sq ft price and ₹40 per sq ft cost store area_sqft 15, stickering_price 900 and stickering_cost 600: a Stickering Price of ₹3,600, a cost of ₹2,400 and a Stickering Margin of ₹1,200. Both amounts are per sq ft, so the Margin compares like with like.
- Sell Stone and Edit sale keep the labels "Stickering Cost (₹)" and "Stickering Price (₹)" and change the hints to "Per sq ft, paid to the engraver" and "Per sq ft, charged to the customer" ("Per piece, ..." for Memorial). Sell shows the working live under the two fields (`4 × 15 sq ft × ₹60/sq ft = ₹3,600 stickering`), the Order Summary shows a "Stickering Price" total under Stone Sale Price when any line has Stickering, and a Stickering line reads `Stickering {qty} × {area} sq ft × ₹{rate}/sq ft = ₹{total}` (`Stickering {qty} × ₹{rate} = ₹{total}` for Memorial) in the cart, the customer's sale history and Edit sale. Two cart lines merge only when their Stickering rates are equal.
- `record_sale` and `correct_sale` take `p_stickering_cost_rate` and `p_stickering_rate` and `record_bill` lines carry `stickering_cost_rate` and `stickering_rate`; the per piece `p_stickering_cost` and `p_stickering_price` signatures are gone. The existing refusals stand ("Stickering cost must be a number", "Stickering price must be zero or more", ...), and a rate whose per piece figure would reach ₹1,000 crore is refused ("Stickering Price per piece is too large", "Stickering Cost per piece is too large"). `correct_sale` re-derives both figures from the Sale's kept Area, or the new Batch's Area when the Batch changes. A one-time migration converted every earlier Sale (rate = old per piece amount / its Area, Area 1 for Memorial) and refuses to run if any Sale's Stickering Cost or Stickering Price would change, so revenue, margin and every KPI were untouched. `v_sales` and `v_chat_sales` expose `stickering_rate` and `stickering_cost_rate`.
- Margin = qty × (sale_price − landed_cost) + qty × (stickering_price − stickering_cost), with each per piece figure derived from Area and its rate as above. Margin % = margin / (qty × (sale_price + stickering_price)).
- FIFO Listing shows Batches of the chosen Stock Line with Available > 0, oldest first, with Ageing Band. Any Batch may be picked; nothing is blocked or confirmed.
- Payment Mode enum: CASH, UPI, BANK_TRANSFER. A Sale is paid in full unless its Bill was sold on credit (Credit below). A Bill may be paid in more than one mode (Payment Split above).
- Credit (client call of 2026-10-31, tickets 62 and 66): a Bill can be sold on credit. `bills.on_credit` is a fact typed on Sell Stone (the Part payment switch) and stays true after the Bill is paid off. The balance is never stored: `v_credit` is the Bill total minus everything received, `bill_payments` (paid at the sale, may add up to less than the total on a credit Bill, zero paid allowed) plus `credit_payments`. A later payment is one receipt: `credit_payments` (bill, paid_on, audit) with `credit_payment_lines` (receipt, payment_mode, amount, primary key receipt plus mode), so a receipt holds several modes and edit and delete act on the whole receipt. Members cannot write any of these tables; `record_bill`, `record_credit_payment`, `correct_credit_payment`, `delete_credit_payment` and `extend_pay_by` do.
- `record_bill(customer, sale date, payments, lines, on_credit, pay_by)` with `on_credit` true saves the Bill, the payments made now and the first pay-by date in one call. Payments are {payment_mode, amount} with every amount typed, zero amounts dropped, and their sum must be less than the Bill total ("Paid now must be less than the bill total of ₹10000"). The Walk-in Customer is refused ("Credit needs a named Customer"). A pay-by date on a bill that is not on credit is refused, and so is one before the sale date or more than a year after today.
- Pay-by dates: `credit_promises` (bill, pay_by, audit) keeps every promise; the first is the original and the latest is the current. `private.default_pay_by(sale_date)` gives the Saturday of the sale week; a Saturday sale goes to the next Saturday and a Sunday sale to the coming Saturday. `extend_pay_by(bill, date)` adds a row: the new date must be after the current one, not in the past and within a year, and a closed or non-credit Bill is refused. `v_credit` returns `pay_by`, `original_pay_by`, `extensions` and `days_left` (current pay-by minus today in IST, negative once late); the colours are left to the screen.
- Later payments: `record_credit_payment(bill, paid_on, payments)` takes a date from the sale date to today (IST) and one or more modes with an amount each (above zero, each mode once). The total of the receipt cannot exceed the balance ("₹5000 is more than the balance of ₹4000"); a Bill at zero balance is closed and takes no more ("Nothing is owed on this bill"). Any Team Member but a Viewer records one. `correct_credit_payment` and `delete_credit_payment` are Admin only; an edit is checked against the balance without that receipt, a delete always works and the balance comes back.
- Credit Bills and Corrections: `follow_bill_total` leaves a credit Bill's payments alone and lets the balance move, but refuses a Correction or delete that takes the total below what was already received ("₹8000 is already paid but the bill total is now ₹6000"). Edit sale cannot send a Payment Split for a credit Bill ("Payments on a credit bill are changed on the Credit page"). `delete_bill` takes the promises and later payments with it. There is no write-off.
- Credit screen: a nav item after Customers (also in the mobile More sheet) with a card per credit Bill: customer, Bill date and total, a due badge, a paid-of-total bar, the balance, the pay-by line ("Pay by Wed 11 Nov, was Sat 31 Oct") and Change date and Record payment. Overdue first (then by pay-by date), KPIs Outstanding, Bills on credit and Overdue over open Bills, search by name or phone, chips Overdue first, Pay-by date and Paid (settled Bills). The badge is green when far, yellow at 2 days or fewer left including the day itself, red once passed ("3 days late"), with an "Extended N×" tag. An expanded card lists the payments, with edit and delete icons for Admin only.
- Elsewhere: the Customer page has a Balance KPI and each credit Bill row shows its balance and due badge; the Customers list and the Sell Customer picker show "Owes ₹X · late" (red when overdue, amber when due within 2 days). `v_customers` exposes `owed` and `credit_days_left`. Selling is never blocked by what a Customer owes. Lifetime revenue still counts the full Bill.
- Daily Sales: a nav item after Credit at `/sales` (in the mobile More sheet) that reviews one day. `/sales` is today in IST and `/sales?date=2026-10-31` is any other day; a date that is malformed, before 2000 or in the future falls back to today. A date field, previous and next arrows and a Today button move between days, and next is disabled on today. `daily_summary(p_date)` returns Billed and Margin over Sales with that Sale date (Margin % as in the Margin formula, null when nothing is billed), Money received per mode from `v_payments` by `received_on`, so it equals `received_by_period` for that day, and Added to credit, each credit Bill of that Sale date's total minus its `bill_payments`. A future date is refused ("The date cannot be in the future"). Square feet sold: `daily_summary` also returns `sqft`, the sum of quantity × `area_sqft` over that day's Sales, and `customer_sqft`, one row per Customer with their sum, largest first, and null for a Customer who bought only Memorial, whose row reads "Memorial only" and sorts last. The Walk-in Customer is one row like any other. Square feet sold sits beside Billed, and a Square feet by Customer list follows the Sales table on a day with Sales. Below the totals, the Sales table of the Customer page with a Customer column in place of Date, newest entered first, with the same Admin edit and delete actions, then a read-only Later payments list of receipts received that day, shown only when there are some. Editing a Later payment stays on Credit. An empty day shows zeros and "No sales on this day". Nothing new is stored.
- Overview shows Outstanding beside MTD Revenue (issue 102, settled with the client): the sum of the Balances of open Credit Bills today, the same figure and format as the Credit screen's Outstanding KPI, so it is shown in full rupees rather than compact. It is the only thing a part-paid Bill changes on Overview. Money received and Daily Sales keep counting each payment on the day it comes in, so a ₹10,000 Credit Bill with ₹6,000 paid Monday and ₹4,000 paid Thursday shows ₹6,000 then ₹4,000 there, while Outstanding reads ₹4,000 on Monday and ₹0 on Thursday. MTD Revenue, Margin and Margin % still count the full Bill at its Sale date. Nothing waits for full payment.
- Not in this version: email or push reminders, and Ask chat seeing credit (`v_chat_payments` still shows only what was paid at the sale).
- Dates are `date` columns in IST: `private.ist_today()` is the reference for future-date checks and Age, whatever zone the server runs in. A Sale date cannot be before its Batch's purchase date. Past Sale dates are allowed back to the Batch purchase date; future dates are rejected.

## Corrections

- Admin only. Edit and delete on Batch and Sale via SQL functions that re-balance Available and re-snapshot Landed Cost where a Sale's Batch changes.
- Refused if the result would make any Batch's Available negative.
- Archive (`archive_batch`) works on any Batch, sold from or not, and is undone by Unarchive. An archived Batch is left out of Sell, Stock Lines, the Public Catalog, the stale panel, Recent batches on Inward, Active stock, inventory value and the "vs last month" figure. Its Sales and their margins stay, and so do units sold in the donut and fast movers. `record_sale` refuses an archived Batch, and `correct_sale` refuses moving a Sale onto one but still edits a Sale already on it. Delete is limited to Batches that are archived and have no Sales: archive first, then delete from the Yard or Recent batches under Show archived.
- A Batch purchase date cannot be moved later than its earliest Sale; the refusal names that date.
- `updated_at` and `updated_by` on Batch and Sale. No audit log in Phase 1.
- Available on mobile as well as desktop.

## Ageing

- Two settings: `ageing_after_days` (default 90) and `stale_after_days` (default 180), with ageing < stale enforced.
- Age = today − purchase_date. Band computed in the view; nothing stored.
- Yard age filter offers >90, >180, >365 days.

## Access

- Google OAuth only. `team_members(email, role)` is the allowlist; RLS on every table checks the JWT email against it.
- Roles ADMIN, YARD_OPERATOR and VIEWER. All read everything including costs, Landed Cost, Margin and the Ask panel. ADMIN additionally: Corrections, Settings, Team Members, Products admin.
- A VIEWER writes nothing: no Sales, Bills, Inward, Customers, Suppliers, Later payments, Pay-by dates, Corrections, Settings, images or Team Member changes. The database refuses every attempt with "A Viewer cannot change anything" and the UI hides the write controls. `is_member()` means "may read"; `can_write()` (ADMIN or YARD_OPERATOR) means "may write".
- Sell and Inward stay open to a VIEWER as look-up screens: the pickers and fields work, a "View only" notice says why, and every button that adds or saves is gone, so nothing can be submitted. Settings shows a VIEWER Team & access and the ageing bands read-only. The Admin-only Catalog images and Product and Supplier lists stay Admin-only; those Products and Suppliers are read on Inward.
- First ADMIN is seeded by migration as aravinthanrc@gmail.com for development; swap for the client's email before handover. Invite = admin adds email + role to the list; no email is sent. Removing the row revokes access on the next request.

## Public Catalog

- Route `/catalog` on the app domain, no tenant slug.
- Lists Stock Lines with Available > 0 with exact counts, filterable by Category. No prices, costs, suppliers, batches or dates. Photos: one per Product, set by an Admin in Settings (Catalog images), stored in the public `product-images` bucket (2 MiB, webp, jpeg or png, shrunk in the browser to 1200 px) and shown only on the Public Catalog and its preview.
- `settings.catalog_public` toggle; when false the route returns 404.
- "Call to Inquire" opens `wa.me/{settings.whatsapp_number}` with a prefilled message naming the Stock Line. Nothing is recorded.
- Served from a `v_public_catalog` view granted to the anon role. It and `v_public_business` are owner-run views by design (ADR 0003); the Supabase advisor warning on them is expected.

## Dashboard definitions

| Total inventory value | SUM(available × landed_cost) over Batches that are not archived |
| MTD Revenue | SUM(qty × sale_price + qty × stickering_price) for Sales in the current calendar month (IST). |
| Outstanding | SUM(balance) over open Credit Bills in `v_credit`, today. Not month to date. Same figure and format as the Credit screen's Outstanding KPI. |
| MTD Margin | SUM(margin) for the month; % = margin / MTD Revenue |
| Square feet sold this month | SUM(qty × area_sqft) for Sales in the current calendar month (IST), `mtd_sqft`. Reads the Area stored on the Sale. Memorial has no Area and is left out. No chart. |
| vs last month | Active stock now vs Active stock at the last day of the previous month, computed as bought-before minus sold-before that date |
| Stock status donut | All-time: SUM(available) vs SUM(units sold) |
| Fast vs slow moving | Units sold in the last 90 days grouped by L × B (thickness ignored), top 5 descending. Memorial shown as one bar per Product. |
| Margin by week / month | Margin for each of the last 12 weeks (Monday start) or 12 calendar months (IST), oldest first, the current one last. Same Margin and billed formulas as MTD; archived Batches' Sales count. A period with no Sales shows 0 and no percentage. |
| Margin by payment mode | The Margin card's Table view: one row per Payment Mode (Cash, UPI, Bank Transfer, always all three) with Collected (sum of payment amounts), Margin, Margin % and Share of Margin, then a Total. A mixed Bill's Margin is shared across its payments in proportion to amount, by running sums rounded to the paisa so the rows add up exactly; a Sale without a Bill counts fully to its mode. A later payment on a Credit Bill counts under its own mode on the Bill's sale date (the Margin follows the sale), and one extra Unpaid row carries each credit Bill's balance and its unpaid Margin, so Collected and Margin still add up to the Bill totals and the Total equals Margin; it shows only when something in the range is unpaid. Range: Week is this week from Monday, Month is this calendar month, both to today in IST; Custom is any start and end date, end not after today. `payments_by_mode(p_range, p_from, p_to)` over `v_payments`. The Chart view keeps its last 12 weeks or months. |
| Money received | A full-width Overview card under Margin and Top customers: a stacked bar chart and a table together, with a Week, Month or Custom picker. Cash, UPI and Bank Transfer columns plus a Total, summed from the payment amounts of `v_payments` (money actually received, never Margin share), so a ₹30,000 Cash + ₹20,000 UPI Bill adds 30,000 to Cash and 20,000 to UPI in the same period and a Sale without a Bill counts fully under its one mode. Week and Month show the last 12 weeks (Monday start) or calendar months in IST, oldest first in the chart and newest first in the table with the current one marked "now", plus a Total row; every period is present, zero when empty. Custom shows one bar and one row per day, end date not after today. A payment made at the sale is dated by the Sale date; a later payment on a Credit Bill is dated by the day it was received, so a ₹4,000 payment on 6 Nov counts on 6 Nov and not on the Sale date. UPI uses `--chart-1`, Cash the muted grey, Bank Transfer `--chart-5`. `received_by_period(p_range, p_from, p_to)`. |
| Top customers | The 5 Customers with the highest billed total (stone plus Stickering) in the chosen window: this month (IST), last 90 days (default) or all time. Each shows the billed amount, a bar scaled to the top Customer and their top 3 Products by pieces, then "+N more". The Walk-in Customer is ranked like any other; archived Batches' Sales count. |
| Stale stock panel | Batches in the Stale band with Available > 0, oldest first, top 4, link to Yard filtered by Stale |

## Yard view

- "Group by" picks Slot (the default) or Size. It lives in the URL (`?group=size`), is not remembered between visits, and narrows with every filter and sort.
- Group by Slot: one section per Stack (Slot plus Batch number), ordered by Slot then Batch number, with Batches oldest first inside (Newest first as the only alternative sort). Batches without a Batch number share a final "No batch number" section. No slot tabs or size sub-tabs.
- Group by Size: one section per exact length and breadth, thickness ignored, as in Fast vs slow moving; no ranges. Sections run smallest length, then smallest breadth, headed like 4 × 2 ft, with Batches of every Product and Slot together and each card showing its Batch number. Batches with no Size share a final "No size" section. Stock Lines, Clamps and the available count work as in a Stack.
- Filters: search text (also matches the Batch number), Slot, Product, Thickness, Supplier, Age.
- Sold Out Batches hidden by default, "Show sold out" toggle. Archived Batches hidden by default, "Show archived" toggle; their Available is left out of the Stack's count.
- "Less than 5 left" toggle (`?low=1`) keeps only Batches whose own Available is under 5; Stack and Stock Line totals are not used. It narrows with every other filter and leaves Sold Out to "Show sold out", so it shows 1 to 4 left by default and 0 to 4 with sold out shown.
- The Slot filter lists the built-in slots, then typed slots alphabetically, which is also the Stack section order.
- Within a Stack, Batches are shown grouped by Stock Line (lines ordered by their oldest Batch) so a Clamp separator sits between every pair of consecutive Batches of the same line, labelled "New batch arrived N days later".
- `/yard?line=<line_key>` deep-links to one Stock Line, showing every Stack that holds it; the palette and the stale panel use it. The Age filter includes a "Stale band" option that follows the configured threshold.

## Navigation

- Desktop: sidebar Overview · Inward Stock · Sell Stone · Yard Slots · Customers · Credit · Daily Sales · Public View Link, Settings from the profile block. ⌘K palette searches pages, Stock Lines (jumps to Yard filtered) and Customers.
- Mobile (< 768 px): tab bar Overview · Inward · Sell · Yard · More; More sheet holds Customers, Credit, Daily Sales, Public Link, Settings, Sign out. No palette.

## Chat

- The Ask panel on Overview answers questions about stock and sales in text and charts. Every Role can use it. It reads, never writes.
- The model sees the `v_chat_*` views only: batches, stock lines, sales, payments, customers, KPIs, products and suppliers. `v_chat_payments` has one row per payment of a Bill or of a Sale without a Bill, with its shared Margin. Never Team Member emails, notes, settings, or any Customer name or phone; Customers appear as a Customer alias.
- Each question returns at most 500 rows.

## Explicitly out of Phase 1

- Credit sales and dues
- Receipts or invoices printed from a Bill
- Merge tool for duplicate Products or Customers
- Audit log
- Offline mode or service worker
- Cost hiding for Yard Operators
- AI assistant beyond the read-only data chat, seasonal comparison, WhatsApp Business API
